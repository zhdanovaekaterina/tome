# Правила организации кода

## Архитектурные границы

Правило зависимостей (стрелки только вправо):

```
api → application → domain → reference → shared
api → identity
infra → (реализует порты всех слоёв)
```

- **`domain`** не импортирует `infra`, `api`, `application`.
- **`reference`** не знает про `domain`.
- **`shared`** не импортирует ничего из проекта.
- **`api`** не импортирует `domain` напрямую — только через `application`.
- **Pydantic** — только в `api/`. Domain и application не импортируют Pydantic.
- **DTO** — маппинг модель → DTO только в `api/`.

См. `docs/adr/0001-reference-domain-split.md`.

## Минимальность изменений

- Вносить минимально необходимый набор изменений для задачи.
- Не рефакторить код, не связанный с текущей задачей.
- Не переименовывать публичные API без необходимости.
- Не переносить код между файлами только ради стиля.
- Не создавать новые абстракции без необходимости.
- Не добавлять интерфейсы, базовые классы, фабрики, адаптеры и слои ради формального соответствия ООП.

**Исключения** (часть архитектурной спецификации):

- Порты — `Protocol` (репозитории, сервисы).
- ABC — для иерархий (`FeatureDefinition`, `SpellStrategyDefinition`).
- Factory — `CharacterFactory` (создание агрегата).

См. `docs/adr/0012-abc-for-own-protocol-for-foreign.md`.

- Не добавлять валидацию, fallback, retry или обработку ошибок, если этого не требует задача, архитектурная спецификация или существующий контракт.

**Исключение:** обработка ошибок **обязательна** на реальных границах — Postgres, Redis, HTTP от клиента.

- Перед созданием нового класса или helper проверить, нет ли уже подходящей реализации.

## Явность и простота

- Код должен быть понятен при чтении сверху вниз без разбора сложных вложенных выражений.
- Явность важнее краткости. Количество строк не является целью.
- Не объединять несколько логических шагов в одно выражение, если это ухудшает читаемость.
- Если промежуточное значение представляет отдельный смысловой шаг — вынести в переменную.
- Последовательность разных логических действий выражать последовательными шагами.
- Не создавать метод ради механической обёртки над существующим методом.
- Дополнительная абстракция должна скрывать реальную сложность или предоставлять реально используемый контракт.
- Не использовать возможности Python ради сокращения строк или демонстрации сложного синтаксиса.
- Если простая конструкция читается лучше сложной — использовать простую.
- Не оптимизировать код по количеству строк или вложенных выражений.

## Преобразования и данные

- Если значение уже приведено к нужному виду — использовать результат повторно.
- Не выполнять повторно `strip`, `lower`, преобразование формата над одним значением без необходимости.
- Не добавлять преобразования, проверки, fallback ради перестраховки.
- Каждое преобразование должно решать конкретную задачу.
- Доверять контрактам методов, типам и внутренним инвариантам системы.
- Не добавлять защитный код для сценариев, нарушающих контракт и не происходящих в нормальном потоке.
- Реальные внешние границы обрабатывать явно: пользовательский ввод, HTTP, файлы, БД, внешние API.
- Защищать **реальные границы** системы, а не каждую строку кода.

## Модели и типы

- **Value-objects** — `frozen dataclass` (`DiceRoll`, `SpellData`).
- **Модели персонажа** — mutable (`CharacterModel` меняется при каст / levelup).
- **Enum'ы** — `enum.Enum`, не строковые константы.
- **Typed IDs** — `NewType` или `frozen dataclass` с одним полем.
- **Никаких `Any`** — типизировать всё. Если `Any` неизбежен — обосновать комментарием.

## Различия между классами

- Различия между классами персонажа — через стратегии (`SpellStrategyDefinition`) и фичи.
- **Никаких** `if class_alias == "wizard"` в domain.
- Если видишь такой `if` — это баг архитектуры, а не решение.

## Классы и файлы

- Основная бизнес-логика находится в классах.
- Один публичный класс на файл.
- Имя файла соответствует имени класса в `snake_case`:
  `BuildService` → `build_service.py`.
- Небольшой спутник, используемый только этим классом (исключение, DTO), может быть в том же файле.
- Не создавать класс-обёртку на одну строку.
- Не создавать класс только для одной статической функции.
- Не создавать файлы заранее без реализации.

**Для actions:** каждый `Action` — отдельный файл (`learn_spells.py` → `LearnSpellsAction`). Исключение — мелкие actions, используемые только в одном месте.

## Тесты

- TDD: сначала тест, потом код.
- Публичные методы покрываются тестами. Приватные — через публичные.
- `shared` — простые тесты без моков.
- `reference` — тесты на реальных заклинаниях (Fireball, Ice Storm, Scorching Ray).
- `domain` — через фейки репозиториев (in-memory).
- `api` — через `TestClient`.
- Интеграционные — с testcontainers, отдельный маркер `@pytest.mark.integration`.

См. `docs/adr/0013-tdd-on-core.md`.

## Пустые строки и форматирование

- Пустые строки разделяют логические блоки.
- Связанные операции — визуально сгруппированы.
- Несколько последовательных присваиваний одного логического шага — один блок.
- Не вставлять пустую строку после каждого отдельного присваивания.
- Ветки `if/elif/else` и блоки `for/while/try/except/finally` — визуально читаемы.
- Перед `return` допускается пустая строка, если она отделяет подготовку от возврата.
- Использовать `ruff format` с настройками проекта. Стиль зафиксирован в `pyproject.toml`.

## Логирование

- Никаких `print()`. Только `structlog`.
- Логи — структурные (JSON), с `event` и контекстом.
- Correlation ID — для трейсинга запросов.

## Git

- Conventional Commits: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `style`.
- Основная ветка — `main`.
- Feature-ветки — для крупных фич (> 1 дня).
- Merge с `--no-ff`. Squash — только для мусорных веток.
- Удалять ветки после merge.
- Tag'и — на релизах.

См. `docs/adr/0015-conventional-commits.md`.

## Версионирование

- SemVer: `MAJOR.MINOR.PATCH`.
- До MVP — `0.x.y`, ломать свободно.
- MVP — `1.0.0`.
- `CHANGELOG.md` обновлять перед релизом через python-release.

См. `docs/adr/0016-versioning.md`.

## Главный принцип

Писать минимально необходимый код, который явно выражает требуемое поведение.

- Простое решение предпочтительнее короткого.
- Явное решение предпочтительнее «умного».
- Реальная необходимость предпочтительнее гипотетической.
- Архитектура должна **ограничивать** сложность, а не создавать её.
