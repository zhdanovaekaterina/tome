# 0016. Версионирование проекта

## Статус
Принято

## Контекст
Проект — приложение (не библиотека). Домен сложный.
Справочники меняются редко, API — часто в MVP, ядро — с каждым рефакторингом.
Внешних потребителей нет пока. Нужна дисциплина для портфолио.

## Решение
SemVer: `MAJOR.MINOR.PATCH`.

### До MVP
`0.x.y`. MAJOR = 0. Ломать API свободно.
- `0.1.0` — shared готов.
- `0.2.0` — Reference модели.
- `0.3.0` — Domain модель.
- `0.4.0` — FSM работает.
- `0.5.0` — Build волшебника end-to-end.
- `0.6.0` — Cast работает.
- `0.7.0` — API + Postgres.

### MVP
`1.0.0` — первый публичный релиз.
- API стабилен.
- Схема БД стабильна.
- Build волшебника работает end-to-end.
- README готов.

### После MVP
Строгий SemVer.

### MAJOR (ломающее)
- Несовместимое изменение API (переименование endpoint, изменение формата ответа).
- Несовместимое изменение схемы БД (без миграции).
- Смена модели справочников (`FeatureDefinition` разбит на 10 типов).
- Смена формата сериализации `CharacterModel`.
- Удаление endpoint (даже если не используется).
- Переименование enum со сериализацией.

### MINOR (новое, обратно совместимое)
- Новая функциональность (endpoint, класс, фича, action).
- Новое опциональное поле в ответе API.
- Расширение справочника (+20 заклинаний, +1 класс).
- Расширение сценариев (build варвара, мультикласс).
- Обязательное поле + миграция.

### PATCH (исправления)
- Багфиксы (Fireball не то урона, спасбросок неверный).
- Правки справочника без изменения структуры (опечатка, damage type).
- Рефакторинг без изменения поведения.
- Улучшения производительности (индекс, N+1, кэш).
- Обновление зависимостей (патч-версия).

### Пограничные случаи
- Обязательное поле + миграция = MINOR. Без миграции = MAJOR.
- Enum с сериализацией + переименование = MAJOR. Без сериализации = MINOR.
- Удаление endpoint = MAJOR (сначала deprecation в MINOR).
- Изменение формата ошибок = MAJOR.

### Хранение версии
- `pyproject.toml` — единый источник истины.
- `src/tome/__init__.py` — `__version__` через `importlib.metadata`.
- `GET /version` — JSON с версией и коммитом.
- Git tag `v*.*.*` на релизах.

### CHANGELOG
Формат [Keep a Changelog](https://keepachangelog.com/).
Секции: Added, Changed, Deprecated, Removed, Fixed, Security.
Обновляется перед релизом, не после.

### Релизы
Каждые 2-4 недели в активной фазе.
Не каждый коммит. Веха — релиз.

### Автоматизация
- `bump-my-version` для bump + commit + tag.
- GitHub Actions: на push tag → тесты, Docker, release notes.

## Последствия
**Проще:**
- Понятная история версий.
- CHANGELOG для нанимателя.
- Git tags как явные вехи.
- До MVP — свобода ломать API.

**Сложнее:**
- Дисциплина в определении MAJOR/MINOR/PATCH.
- Обновление CHANGELOG перед каждым релизом.
- Миграции БД при MAJOR.
