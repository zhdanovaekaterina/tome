# Правила проекта

## Приоритет правил

При конфликте правил использовать следующий приоритет:

1. **Архитектурная спецификация проекта** (`docs/adr/`, `docs/architecture.md`).
2. **Это правило.**
3. **Правила организации кода** (`docs/coding-rules.md`).
4. **Существующий стиль соседнего кода.**

Не переписывать существующий код только ради соответствия этому правилу.
Правила применяются к **новому** и **изменяемому** коду.

## Стек

- Python 3.14, SQLAlchemy 2.0 (sync), pytest, alembic
- Менеджер зависимостей: pip
- Линтер/форматтер: ruff
- Статический анализатор: mypy

## Команды

- Вся работа в виртуальном окружении, запуск `source .venv3-14/bin/activate`
- Установка: `pip install <package_name>`
- Тесты: `pytest`
- Линт: `ruff check .`
- Формат: `ruff format .`
- Проверка типов: `mypy .`
- Миграции: `alembic revision --autogenerate -m "msg"` / `alembic upgrade head`

## Жёсткие правила

- Не объяснять выполненную работу
- Писать тесты только для публичного интерфейса
- Не писать тесты для переменных классов, геттеров и сеттеров если только у них нет специфической логики
- Не писать реализации методов если только пользователь явно не попросит это сделать
- Коммиты запрещены, только человеком

## Запреты (Hard Rules)

- Не добавлять зависимости в `pyproject.toml` без явного запроса.
- Не писать `print()` — только `logging` через structlog.
- Не использовать `Optional[X]` — только `X | None`.
- Не подавлять исключения: `except Exception: pass` запрещён.

## Архитектура проекта

### Принципы

- **SOLID**
- **Dependency Injection** (через конструктор)

### Слои (снизу вверх)

#### `src/shared/`
- **Назначение:** value-objects, enum, общие сущности для использования всеми слоями.
- **Зависимости:** не зависит от других слоёв (самый нижний слой).
- **Импорты:** —

#### `src/reference/`
- **Назначение:** справочники D&D.
- **Зависимости:** может импортировать из `shared`.
- **Импорты:** `shared`. Внешние импорты запрещены.

#### `src/domain/`
- **Назначение:** чистые сущности и интерфейсы.
- **Зависимости:** может импортировать из `shared` и `reference`.
- **Импорты:** `shared`, `reference`. Запрещены внешние импорты и импорты реализаций репозиториев.

#### `src/application/`
- **Назначение:** use cases, оркестратор.
- **Зависимости:** зависимости инжектируются через конструктор.
- **Импорты:** `shared`, `reference`, `domain`.

#### `src/infrastructure/`
- **Назначение:** БД-репозитории, адаптеры внешних API.
- **Импорты:** `shared`, `reference`, `domain`, `application`.

#### `src/api/`
- **Назначение:** роутеры FastAPI. Тонкий слой.
- **Поток:** валидация → вызов use case → ответ.
- **Обязанности:** маппинг сущностей ядра в DTO.
- **Импорты:** `shared`, `reference`, `domain`, `application`.

### Правила импортов (сводка)

| Слой             | Может импортировать из                         | Запрещено                                |
|------------------|------------------------------------------------|------------------------------------------|
| `shared`         | —                                              | всё остальное                            |
| `reference`      | `shared`                                       | внешние импорты                          |
| `domain`         | `shared`, `reference`                          | внешние импорты, реализации репозиториев |
| `application`    | `shared`, `reference`, `domain`                | прямые зависимости (только через DI)     |
| `infrastructure` | `shared`, `reference`, `domain`, `application` | —                                        |
| `api`            | `shared`, `reference`, `domain`, `application` | бизнес-логика в роутерах                 |

## TDD-воркфлоу (обязательно)

1. Напиши тест первым. Тест описывает поведение через публичный интерфейс.
2. Запусти `pytest -q` — тест должен упасть по правильной причине.
3. Остановись, реализация функционала за пользователем если в промпте явно не сказано иное. 

**Жёсткие правила TDD:**
- Никогда не менять тесты, чтобы «заставить их пройти».
- Никогда не писать реализацию до теста.
- Один тест = один сценарий. AAA: Arrange → Act → Assert.

## Стиль кода (KISS, DRY)

- Дублирование логики (не синтаксиса) выноси в helper. Дублирование синтаксиса оставь, если абстракция усложняет чтение.
- Никаких «на всякий случай» параметров и YAGNI-абстракций.
- Явное лучше неявного: полные type hints на всех публичных функциях.

## SQLAlchemy 2.0 (жёстко)

- Только 2.0-style: `select()`, `session.execute()`, `session.scalars()`. **Запрещён legacy `Query` API.**
- Сессии только через DI. Никаких глобальных `engine` или `session` в модулях.
- Транзакции явные: `with session.begin():`.
- eager loading явно: `selectinload()` или `joinedload()`. N+1 недопустим.

## Циклы и тупики

- Одна и та же ошибка после 2 попыток фикса → остановись, покажи traceback, спроси.
- Миграция сломала тесты → остановись, не пытайся «починить» тесты под миграцию.
- Если задача требует изменения схемы БД → флаг для ручного ревью.
